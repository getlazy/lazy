# Lazy Development Guidelines

These guidelines apply to all agents working on tasks in this repository.

## Scope: development OF lazy is NOT development WITH lazy

Everything here is about lazy's own codebase, not repositories merely *developed with* lazy — `Dockerfile.lazy`, the e2e harness rules and the Storage invariants are lazy's own; projects built with lazy have their own toolchains. Lazy's images are built and used locally: an image reflecting whoever built it is by design, not a defect.

## Running Lazy

Always `bun run ./src/index.ts <args>` — never `npx bun run`, which hangs indefinitely when stdin is piped (anthropics/claude-code#27401).

## CRITICAL: Never Lose Human Feedback

**The single most important invariant in Lazy.** Human feedback — `$EDITOR` edits, review comments, close reasons, notes — must be durably saved before any operation that can fail (auth checks, Docker launches, network calls) gets a chance to lose it.

1. **Save first, act second.** Persist editor/prompt input to durable storage immediately after the editor closes; only then run anything that might fail.
2. **Pre-flight before editor.** Every check that can fail (authentication, Docker availability, locks) runs BEFORE `$EDITOR` opens. The human must never type feedback only to have a pre-flight failure discard it.
3. **Recovery files.** If content cannot reach the database yet, write it to `.lazy/recovery/` — these survive crashes.
4. **Never silently discard.** If feedback cannot be delivered (e.g. container launch fails), it must still be preserved, and the human told how to retrieve or re-submit it.

## Architectural Invariants

Load-bearing design decisions, each learned the hard way. Do NOT change, "optimize away," or weaken them without explicit human approval.

### Upstream merge is sync's job, not unblock's

Unblock only delivers feedback, with zero network dependencies. Upstream merges happen via `lazy sync <task>`, daemon signals, or the builder.

**Sync reconciles the task branch in two ordered steps, and only the task branch.** Step 1 merges `origin/<task-branch>` when it has commits the local branch lacks (a colleague pushed to it); step 2 is the parent merge through `resolveUpstreamMergeRef()`. Both agent-resolve conflicts. The order is load-bearing: merging the parent into a branch still missing a colleague's commits produces a merge accept will not reproduce. Step 1 detects via `driver.fetchBranch`, deliberately NOT `remote-sync.ts`'s `detectExternalChanges`, which answers a different question (was this task's PR/MR merged or closed elsewhere). It is skipped with a one-line phase reason (driver `local`, offline, branch not on origin) and never throws — a fetch failure must not block step 2. Neither step touches, merges into, or pushes the PARENT branch, and sync pushes nothing at all: the reconciled branch reaches origin via the existing after-turn push and accept.

**A sync RESTORES the status it found, and `submitted` is the only status it restores.** A merge changes nothing about where the task stands with its reviewer, so the launch records the status inside the same lifecycle lock as the `working` transition (`sync_restore_status` task metadata, `src/task/sync-restore-status.ts`) and the reconciler's sync park reads it once and clears it. Without it, every sync — manual, the auto-sync after an upstream accept, the retry loop, reparent's — quietly relabelled a task with an open PR `blocked`, dropping it out of the submitted view and off PR-comment auto-react, which is gated on `submitted`. `blocked`/`conflict` are never recorded or restored: they are the DERIVED paused label (`parkTaskPaused`), and a derived `conflict` therefore WINS over a restored `submitted` — a sync can merge a protected file in, and that label is what accept gates on. `interrupted` is not restored either: a completed sync is positive evidence the worktree is healthy. **The marker NAMES ITS OWN TURN** — it carries the sync's command id, and a reader gets the status back only when the turn it is parking presents that id, which is what makes a leftover marker inert rather than merely unlikely to be misread. A CRASHED sync restores too (`handleErrorResponse`), and that reader sees every turn type, so without the id a marker left by a sync that died with no response could be claimed by an unrelated work turn crashing fatally turns later — parking `submitted` on a task nobody submitted. A mismatched read changes nothing and does not clear the marker. **A killed sync is never a "stranded completion"** either, for the same reason a cluster is not: a sync's commits are the merge, landed mid-turn, so a sync killed between its two steps has commits and is half done — `recoverStrandedCompletion` gates on `status.command_type === 'sync'` and lets it fall through to `interrupted`. **The statuses sync dispatches from are one list** — `SYNC_DISPATCHABLE_STATUSES` (`src/task/sync-dispatch.ts`), read by both `syncTaskRun`'s in-lock whitelist and the daemon's retry loop; the loop's own copy was missing `submitted`, which only became visible once a synced task stopped landing in `blocked`, where a task's `pending_sync` would have been held forever undrained. Reasoning and coverage in [docs/sync-restores-submitted.md](docs/sync-restores-submitted.md).

**A `working` task is syncable by exactly one caller: its own running agent.** Sync's 409 on `working` stands for humans, the builder, and any other task's agent — including for a direct subtask, which passes the ownership gate and is still refused. Only `SyncTaskParams.callerTaskId === task.id` gets through, and the MCP boundary sets that from the authenticated per-task context, never from a tool argument. There the last leg changes and nothing else: `syncTaskRun` still makes every decision (fetch, `resolveOriginTaskBranch`, `resolveUpstreamMergeRef`, both containment tests, `pending_sync`), then hands the two ordered merges to `runSelfSync` (`src/daemon/self-sync.ts`), which performs them with plain git in that agent's worktree while the agent is parked inside its `lazy_sync` call — no supervisor, no second session, no `claude -p` conflict pass. This is what lets a cluster task, which is `working` for its whole turn, stop cutting every child from the base its parent had when the cluster started.

The call merges everything outstanding and stops at the FIRST conflict, leaving that merge in place; the agent resolves it, concludes it with `lazy_commit`, and calls `lazy_sync` again. **No step state is stored anywhere** — the repeat call re-derives the plan, and the step that landed is not offered again because HEAD contains it. A merged step is recorded as a `supervisor`-actored `sync` turn with NO SHA window (the calling agent's own work turn already spans those commits), and the route never changes status or records commits: the turn it runs inside owns both. Details and the two refusals in [docs/self-sync-while-working.md](docs/self-sync-while-working.md). **A merge is never evidence a turn finished, either.** Because the self-sync route records no commits, an agent that syncs itself and then crashes leaves the merge as the ONLY unrecorded commit — and `recoverStrandedCompletion` used to read that as a finished turn and park the task `blocked` behind a bogus "[Recovered]" turn. It now ignores every unrecorded commit with a second parent when deciding whether the agent finished, and asks its real-work question of each remaining commit against its own parent, so a range spanning a merge can never pass off upstream changes as the agent's work. That is an exclusion from the INFERENCE only: when real work does trigger recovery, the merges are recorded like everything else through the unchanged `recordSessionCommits` rules.

### A lazy comment never starts a turn

A `Comment` created through lazy — `lazy comment`, the web UI, `lazy_comment` over MCP — is persisted and nothing else. It reaches the agent in the prompt of the next `lazy unblock` (or the initial start), in the `NOTES ADDED SINCE YOUR LAST TURN:` block `buildNotesContext()` assembles. Those are the ONLY two note-delivering launches: `launchAskTask` skips notes deliberately (a read-only question must not consume queued feedback) and `syncTask` never builds them. No comment surface may emit a `comment` signal, and nothing may scan comments to launch a turn — a comment that auto-launched a turn raced the human's own unblock ("task is busy") and lost their real feedback.

The delivery cutoff is `session.notes_delivered_through`, advanced by `Storage.markNotesDelivered()` through the newest comment a prompt actually carried (never to "now", so a comment racing prompt assembly rides the next turn). Every surface answering "what has the agent not seen" resolves it through `resolveNotesCutoff()` (`src/task/turn-context.ts`) — never "new since the last agent turn", which ask and sync turns silently skip past.

FORGE (PR/MR) comments are the one exception, opt-in behind `[daemon] auto_react_comments`: nobody is sitting at a lazy CLI about to resume the task. `deliverPendingSignals` tells them apart by `details.source === 'remote'`; a `comment` signal without it is consumed WITHOUT delivery, so a stale queue cannot resurrect the auto-launch. Details in [docs/comment-delivery.md](docs/comment-delivery.md).

### A `cluster` task drives its children, and the driver — not the daemon — decides how many run at once

A `cluster` task's agent (its DRIVER) runs its own subtasks instead of doing the work itself: brief, schedule, wait, review, unblock or accept. The behavioural half is `src/prompts/cluster-constraints.md`, injected per TURN from `task.type` (`src/task/type-constraints.ts`), NOT baked into the stored prompt the way `lazy fix`/`document`/`refactor` bake theirs in: a cluster runs for many turns, is created from four different surfaces, and a prompt edit must not be able to drop the rules mid-run.

**THERE IS NO CONCURRENCY RULE, and its absence is the load-bearing decision.** The type was called `loop` until 2026-09-20 and `assertLoopHasNoRunningChild` refused to START a second child while one was active. The engineer reversed it after ten days of running them: the N*(N-1) sibling merges the serial rule avoided were mostly micro-conflicts, while the serialisation itself was slow enough to dominate — two small children took 1h46m and 1h10m of wall-clock each, most of it waiting. The driver now decides, weighing file overlap, dependency between children, and what each accept costs the siblings still running. Do not reintroduce a cap or a queue in any form: agent tasks are deliberately uncapped (the agent concurrency cap, its queue machinery and the idle reaper were all removed in 2026-08), and a daemon refusal cannot see what the driver can. The fix-round budget below is the only bound, and it is per CHILD precisely so siblings never couple through it. The reversal is recorded in `docs/design/cluster-replaces-loop.md`.

The enforced half is one daemon rule:

- **A child added to a BLOCKED cluster starts a turn** (`src/daemon/cluster-restart.ts`). This is the one local event that launches a turn, and it does not weaken the comment rule above: no comment is read, no `comment` signal is emitted, and the trigger is a change in the TREE, derived by the reconciler against a per-cluster watermark. Derived rather than emitted even though `parent-child-tap.ts` gives the daemon a write-side chokepoint: that tap is the right home for the `[Subtask added]` COMMENT (write once, retry from a queue if it fails), but a turn that was never started cannot be swept up later, and at `createTask` time the cluster is still `working`, so whether it needs waking is not yet knowable. The tap says WHAT changed; the watermark decides WHETHER to wake the cluster. Children created by the driver's OWN agent never wake it, or a cluster that spawns subtasks wakes itself forever. Budgeted through `autoUnblockTask` like every other daemon-started turn.
  **Only a WORK turn raises the watermark's floor** (`startsADriverTurn`). The floor is the start of the driver's most recent turn, and it used to be the latest `human`-role turn of ANY type — but a driver self-syncs mid-turn, and `runSelfSync` records a `human`-role `sync` turn. So a child added at 10:00 to a driver whose turn ran 09:50–11:00 and synced at 10:30 sat BELOW the floor, the candidate list came back empty, the watermark advanced past it, and the child was buried: the driver reported itself finished with a task it never ran. It cost two hand-unblocks on 2026-09-19. Turns recorded DURING a turn — sync, review, ask, nudge — must never raise it.
  **A cluster somebody STOPPED is never woken this way**: `user_stopped` means "do not run this without me", and this path did not ask. It reads the gate through `isUserStopped` (`src/task/user-stop.ts`), the zero-import home of the rule. The arrival is not lost — the message the restart would have carried is written as a COMMENT on the cluster instead, delivered by the next `lazy unblock` whoever sends it. Once per child: the watermark advances on a successful write exactly as on a successful launch.
  The paths that consult the gate are countable, and there are eight: the reconciler's fast auto-resume lane, its daemon-restart interrupt path, the slow lane's queue (`listSlowLaneQueue`), this restart, auto-delivery's `upstream_change` and `ci_result` paths, the replay of a subtask start the usage pause held (`processHeldStart`, src/daemon/usage-pause.ts), which stays held while its parent is stopped, and the wake of that parent once the held start launched (`processParentWake`, same file), which wakes only a CLUSTER parent and writes a comment instead for a stopped or non-cluster one. The delivery paths leave their durable signals queued while stopped, so an explicit resume allows normal delivery to retry them.
  **The exemption lasts until the task's next COMPLETED TURN, whoever started it.** `resetConsecutiveInterruptions` clears the flag, and the `actor === 'human'` conditions on unblock and resume decide only who clears it EAGERLY at launch — every completion path calls it unconditionally afterwards (work and sync turns in `reconcile.ts`, plus `recordAskCompletedTurn` and `recordReviewCompletedTurn`). So a builder's unblock ends the stop one turn later than a human's, not never. **A read-only visitor is enough**: `lazy ask` needs `blocked`/`conflict` and `lazy_review` needs blocked/conflict/submitted/interrupted — the states a stopped task sits in — and both record a completed turn, so asking a stopped task a question lifts its stop, while stopping an in-flight ask or review deliberately never sets the flag (`stopClaimedTurn`). Do not restate this as "the unblock that clears the stop": it is neither actor-scoped nor tied to unblock.

- **A cluster is never a "stranded completion".** `recoverStrandedCompletion` (`src/utils/reconcile.ts`) reads unrecorded non-merge branch commits as proof that the agent finished (merges never count — see the self-sync paragraph above) and only the finalize handshake was lost. For a cluster that inference is false: every `lazy_accept` of a child lands that child's work on the cluster's branch DURING the driver's turn, so from its first accept onwards a cluster killed at any point looked finished and was parked in `blocked` — where, per the rule above, only a NEW child could wake it. The gate is `isClusterTask`, first thing in that function; a killed cluster takes the ordinary `interrupted` → auto-resume path, and nothing is lost because the next finalized turn records every commit since the last known SHA anyway.
- **The per-child fix-round budget is per CHILD** (`src/daemon/cluster-fix-rounds.ts`, `[cluster] max_child_fix_rounds`, default 3). The counter is task metadata on the child, so N children running at once each carry their own and one stubborn child neither spends nor refuses a sibling's. A budget on the cluster as a whole would recouple the siblings that dropping the serial rule uncoupled.
- **A cluster's constraints ride every turn, including the daemon's own.** `typeConstraintsSection(task)` is prepended by all five work-command literals — start, unblock, manual resume, `autoResumeTask`, `autoUnblockTask` — and `test/unit/cluster-type-constraints.test.ts` scans for it mechanically. The recovery paths are exactly the ones that forgot, and they are also the ones most likely to run on a FRESH agent session: `agent_session_id` is only written when a turn FINALIZES, so a turn killed before that leaves nothing to resume and the contract has to come from the prompt. Both resume paths rediscover the session id through `findLatestSessionFile` (`src/agent/session-discovery.ts`) against `runner.agentSessionProjectDir(worktreePath)` — never a private scan, and never `.json`, which is not what Claude Code writes.

Progress (k of n accepted, the running children, the deferred ones) is DERIVED from the children in `src/task/cluster-progress.ts` and rendered by every surface that shows it — no stored counter, which would drift the first time a child was closed, reparented away, or accepted by a human.

**The WIRE says `cluster` too, and the rename travelled WITH the Ruby client.** `clusters` (the RPC), `clusterProgress` (on `show`) and `cluster_progress` (in `lazy show --json`) were held at their `loop` spellings until Lazy Teams could move in the same change, because a rename from the daemon alone breaks a deployed client.

**The compatibility goes on the CLIENT, because the client is the half that runs ahead.** Lazy is a monolith for version management — every project daemon runs the tree the Rails app ships with, rolled by `RollsFleet` on a minute tick — so an OLD app against a NEW daemon cannot arise. The reverse does: after an upgrade the app runs new code at once while each daemon runs old code until the roll, and indefinitely for a project that exhausted `Project::AUTO_RESTART_ATTEMPTS`. So `Client#clusters` falls back to `loops` on `NotFound` (narrowly — a timeout or a 500 must surface as itself), and `ClustersPresenter#entries` reads `payload["clusters"] || payload["loops"]`, because an old daemon answers under the old key and reading only the new one renders "no cluster tasks" for a project that has several. The daemon also keeps answering the retired `loops` METHOD for one release, carrying both keys on that path alone, for any client not on the monolith's release train. Its two `case` arms are tested THROUGH `handleRpc`, since a test calling `handleClusters` directly proves nothing about an arm existing. The two FIELDS carry no compatibility spelling, deliberately: a missing field is an absent progress line, not a failed page. All of it comes out in one commit next release. Details in `docs/design/cluster-replaces-loop.md`.

### One resolution decides which ref a parent branch lives on

Everything that must agree with `lazy accept` about a parent branch — sync's merge target, the base a child branch is cut from, the base a turn diff is rendered against — resolves it through `resolveUpstreamMergeRef()` (`src/remote/upstream-ref.ts`), never `driver.resolveUpstreamRef()` directly. Accept routes an UNPROTECTED target (every intermediate `lazy/...` branch, plus any unprotected named branch) into the LOCAL branch and only a protected target through the forge; `mergeLandsLocally()` is that single routing predicate, called by both.

Neither direction may regress: a parent task's own agent commits can never be on origin (agents have no push credentials), so resolving unconditionally to `origin/<parent>` makes sync say "Already up to date" while accept refuses with conflicts; but the local parent can be BEHIND origin after a forge-side accept, so the remote ref wins whenever it CONTAINS the local branch. They disagree only when local has commits origin lacks, and there accept's routing decides. On disagreement the resolution WARNS (naming both refs, which was used, whether the branch is pushable) and **never pushes the parent** — the engineer may be mid-manual-work on it.

### One resolver decides a task's diff base

Every surface rendering "what did this task change" — `handleDiff` (behind `lazy diff`, the web review surface, Teams' `reviewDiff`), `lazy_diff`, the TUI review, the review editor's turn diff, the `lazy show` summary — resolves its base ref through `resolveTaskDiffBase()` (`src/task-diff-base.ts`), which goes through `resolveUpstreamMergeRef()`. Never compute a base ref locally on a new surface, and never "fix" an implausible diff in the display layer: reading the raw local default branch instead attributed every upstream commit since clone time to one task, a 90k-file diff on a freshly seeded project. `resolveTaskDiffBase` never throws and never fetches — `refreshRemote: false` takes the ref NAME from `driver.upstreamRefName()` while leaving every routing decision in `resolveUpstreamMergeRef` exactly as accept sees it. The REVIEW REGIONS carving is on this list too: it takes its range from `resolveTaskDiffContext` (`src/daemon/task-diff-context.ts`, which calls `resolveTaskDiffBase`), so a region can never be carved out of a range `lazy diff` disagrees with. Details in [docs/task-diff-base-resolution.md](docs/task-diff-base-resolution.md).

### One resolution decides which run speaks for a `working` task

`working(not-alive)` is a promise that the reconciler is about to act, so the label and the reconciler must ask the SAME liveness question. Both go through `src/utils/working-run.ts`: a LIVE ask/review claim that names a run is that run (the claim's runner, and for a review its own `<id>-review` mailbox); otherwise the work run on the SESSION's runner (`session.runner_type`, never the project default); liveness is always `runner.isRunning`, never `getRunInfo`; and a run whose launch is in flight in the daemon (`launchInFlight`, which the reconciler skips) renders `working(launching)`. Probing the work run on the project runner rendered a live reviewer as dead for its whole run after every daemon restart. Never add a read surface that computes the substate from its own probe — call `computeTaskWorkingSubstate` / `probeWorkingRun` / `readTaskWorkingSubstate` (the watch headers).

**An ask/review claim lives only as long as the process that made it.** Every claim carries `claimed_by_process` (`CLAIMING_PROCESS_ID`, `src/daemon/in-flight-turn.ts`); a claim another process made — a previous daemon's, with or without a run name — is ended at once (`abandonPreviousGenerationClaim` in `reconcile.ts`: stop the run, found by its deterministic name when unstamped, then abandon). A restart kills every child's proxy connection, and the restart reaper and shutdown sweep find runs by the WORK run name only, so a reviewer launched by the old daemon survived both and its claim held the task for the 24h backstop. An identity, never a timestamp: a clock step must not make this process's own mid-launch claim look foreign. And `interruptForDaemonRestart` never interrupts a task whose `working` belongs to a live ask/review claim — `interrupted` auto-resumes as a WORK turn nobody asked for; the claim's ending restores `restore_status`. Details and the remote-diagnosis recipe: [docs/working-not-alive.md](docs/working-not-alive.md).

### One resolver decides which commits a task RECORDED, and it never trusts the last record

Every path that writes commit records — the reconciler's three (stranded recovery, post-sync, turn end), a clean host-side sync (`syncTaskRun`, so its merge commit is never mistaken by stranded recovery for a crashed turn's finished work) and `lazy pair`'s end-of-session record — goes through `recordSessionCommits()` / `scanSessionCommits()` (`src/task/session-commits.ts`). Two properties are load-bearing, and both were learned from the same incident. The range ALWAYS starts at `session.git_start_sha` (merge base as the fallback, and nothing recorded when neither resolves), never at a previously recorded commit: `Storage.getSessionCommits` sorts by WRITE time while `git log` answers newest-first, so the array's last element is the OLDEST commit of the last batch, and using it as "last known SHA" walked the range start backwards every turn. And the walk is `--first-parent`, so a merge contributes the merge commit and never the merged-in line — `A..HEAD` is a reachability query, so the first sync recorded the whole upstream branch as this task's work. Together they ratcheted `teams-quality-loop` to 790 records, back to the v0.15 release, for a branch carrying 28. The read-only callers of `getNewCommits` (watch's commit readout, agent-switch orientation, `lazy pair`'s "commits made during this session" summary, and the accept gate's "stale by N commits" on a pending review) pass `firstParent: true` for the same reason — and `test/unit/session-commit-scan.test.ts` enforces that mechanically over every call site in `src/`, balancing parens rather than reading one line, because the flag is opt-in and a call formatted across lines hid its own omission.

The COUNTING twin is on this list too. `countNewCommits` backs the live progress readout and answers the same question, so it walks `--first-parent` in its own implementation — it takes no options, so there is no call-site flag and the guard asserts the implementation instead. That readout also anchors at `session.git_start_sha` and subtracts what is recorded, never at the last recorded commit: it carried BOTH halves of the incident for a release, inflating a live counter the way they inflated the store.

Recording paths only ever ADD. The single delete is `Storage.deleteSessionCommits`, and its one caller is the explicit `lazy system repair-commits`, which reports by default and writes only under `--apply` — a store rewrite that happened as a side effect of a fix would be exactly the silent repair this was asked not to be. Forensics, the four-batch evidence, and the repair's limits: [docs/recorded-commit-range.md](docs/recorded-commit-range.md).

### One entry point runs a search, and one module describes its grammar

Every surface that searches calls `executeSearch()` (`src/search/run.ts`), never
`storage.search()`, `structuredSearch()` or a local `fuse.js` call. There are
four: the daemon's `search` RPC (behind `lazy search`), the `lazy_search` MCP
handler (`createSearchHandler`, which reaches Storage itself rather than through
that RPC), the dashboard's `/search` page, and the command palette's
`/api/search`. Choosing the matching mode (fuzzy / structured / regex), applying
the type filter and explaining an empty tag result are business rules;
`storage.search()` is only the regex mode's backend. Each caller keeps only its
own presentation — paging, the MCP scratch gate, HTML vs JSON vs a table.

Two of the four had their own copy. The dashboard called `storage.search()`
directly, so a `field:` query was parsed by the CLI and run as a raw regex in the
browser: `code:spike` answered 0 on one surface and 4 on the other, from the same
store, and the divergence was invisible to both. The MCP handler re-implemented
all three modes — same rules, separately spelled, which is the same bug one edit
away.

The grammar those surfaces DESCRIBE lives once too, in `src/search/grammar.ts` —
rendered as text by `lazy search --help`, as HTML by the search page's Query
syntax panel, and named in the MCP tool schema. `test/unit/search-grammar.test.ts`
feeds every documented syntax to the real parser, because the failure that
reaches users is not two prose copies disagreeing with each other but one of them
disagreeing with the parser.

Field semantics are part of that description and must match it: `task:`, `goal:`
and every `in:` scope are case-insensitive SUBSTRING matches; `status:` and `tag:`
are exact (both are closed sets). `task:` was `code:` and matched a code only in
full — the rename is clean, with no hidden alias, and `code:<value>` now throws a
QueryParseError naming the replacement rather than silently searching for the
literal text.

### `show` sends the ANSWER, never the rule for a client to re-apply

A task-record surface needs three answers that are rules, not projections: which comments the agent has not seen (`resolveNotesCutoff`), how turns group into review chunks (`groupTurnsIntoChunks`), and which agent reviews COUNT (`isSuccessfulReviewReport` — the same predicate `reviewIssuesAwaitingWork` gates accept with). The `show` RPC answers all three itself: `notes` plus a `delivered` flag on every comment, `chunks`, `reviews`. The wire projections live in `src/task/show-sections.ts` and contain NO rule of their own — each one calls the owning function, and the daemon's own task page and the `lazy_show` MCP tool read the same projections, because a field only remote clients use is the same problem one release later.

`sections` on that RPC is honoured and means: omitted → every section whole (what `lazy show` relies on); named → only those, paged by `offset`/`limit` from the start; unknown name → a 400 naming it. `sectionsServed` and `counts` always ride along, so a caller can tell a section that is EMPTY from one it did not ask for — the silence that sent a Teams port re-implementing two of the three rules in Ruby and refusing the third. Details and the Teams follow-up: [docs/show-derived-sections.md](docs/show-derived-sections.md).

### Identity is the daemon's environment, and a request never carries one

Every attributed row names a person (`actor_email` / `actor_name`). Outside managed mode that person is the daemon's own git config — `git config --get user.email` / `user.name` with the project root as cwd, resolved once in `src/identity/` and stamped once in `applyCallerActor` (`src/daemon/rpc-handlers.ts`). There is no lazy-level override, no second path, and **no request field**: a caller may name the ROLE (the channel a write came through) and never the PERSON, which is a 403. `/rpc/*` refuses user-kind tokens there and `mintActorToken` refuses to mint one — a path that exists and is never exercised is a path nobody checks. In managed mode the reverse holds: git config is not consulted at all and identity rides the caller's token.

Success is cached 60s per project root; a FAILURE is never cached, so someone who has just been refused and fixed their config is believed on the very next command with nothing restarted.

What is refused, in git's own wording ("Please tell me who you are"), is a command that produces an ATTRIBUTED ROW or LAUNCHES A TURN — the second because a turn nobody can be attributed to should not start, since its rows arrive after the caller is gone (`ensureTaskContainer`, `getDaemonMcpConfig`, `builderSlot`, `mintDashboardTicket` are gated for exactly that reason and no other). READS never are — `lazy list`, `show`, `diff`, `search` and `doctor` keep working, because looking at something is the likeliest moment to discover the problem. Neither are the ENVIRONMENT-only writes, which write no row and are how someone recovers from the setup being diagnosed: `concurrency`, `mintActorToken` / `revokeActorToken`, `putUserCredential` / `revokeUserCredential`, doctor remedies. Which commands are which lives in `src/daemon/rpc-command-kinds.ts`, whose partition is enforced by `test/unit/rpc-command-kinds.test.ts` (a new command must classify itself) and whose runtime default is "treat it as a write".

Every CLI command that opens `$EDITOR` or a prompt asks the daemon FIRST (`requireActorIdentity`, the `identity` RPC) — the never-lose-feedback invariant above, and the daemon's environment is the authority, not the shell the CLI happens to run in. `lazy doctor` is the one surface that explains at length; the point of occurrence prints the refusal and one pointer to it. Rationale: [docs/design/actor-identity-and-remote-clients.md](docs/design/actor-identity-and-remote-clients.md) §3.4–3.5.

### An agent's work is attributed to whoever asked for the turn

An agent has no identity of its own: the person on its writes is the TURN OWNER — whoever the daemon accepted the turn-launching RPC from. One record answers it, in `src/daemon/turn-owner.ts`: a PENDING owner decided in `handleRpc` (from the caller's user token, or on a laptop from the daemon's own git config — never a request field), promoted at launch to a durable `(email, name)` on the SESSION. `planTurnCredential` is where the promotion happens because it is the one function every launch path already calls; do not add a second recording point. **The pending owner lives ONLY in the request's `AsyncLocalStorage` scope** (`runAsTurnOwnerRequest`); `getPendingTurnOwner` answers from it and is null outside a request, or inside a request for a different task. Every launch a request performs or queues (a review ask dispatched in the background included — `prev.then(work)` runs `work` in the context `.then` was called from) reads the scope, and concurrent requests on one task each read their own. A turn the daemon starts by itself — auto-deliver, auto-resume, the pending-sync retry loop, a cluster restart — runs outside every request, so it bills nobody even WHILE a member's request on the same task is in flight. Do not bring back a shared per-task record in any form, as a fallback or otherwise: it existed, first cleared per outcome and then in a `finally` at request end, and every version billed a member for a daemon-started turn that raced their request. A request-driven launch that must bill its asker has to run inside that request's async chain; if one ever cannot, capture the owner explicitly (as `claimSyncTurn` captures it onto the in-flight claim), never through a shared slot.

Three things about it are load-bearing. **The write is unconditional, including the null**: a launch with no pending owner CLEARS the previous turn's person, so the reconciler's auto-resume, auto-deliver and a sync nobody asked for record NO ASKER instead of inheriting whichever human touched the task last (what their rows then NAME is the next section). The two directions therefore FAIL differently, and that asymmetry is the rule, not an implementation detail: failing to write a PERSON is best-effort and is FOLLOWED BY A CLEAR, which is what makes "the rows name nobody" true rather than hopeful — the record the failed write did not overwrite is the PREVIOUS turn's, and leaving it would name a different person or the automation account; while failing to CLEAR one is retried, then VERIFIED by reading the session back, and then REFUSES THE LAUNCH. A write reporting success is not proof it happened — `FileStorage.setSessionTurnOwner` returns silently when it cannot resolve the session and `RemoteStorage` refuses the call outright — and a refused launch is retried on the next pass, while a row durably stamped with somebody who did not ask for the work is not repairable. **The record is on the session, not in memory**, because an agent writes for the whole length of a turn and the daemon that reads the owner back is frequently not the daemon that recorded it — the request scope, which is still what BILLING reads (`getTurnOwner`, narrowed to a `spendable` token-derived owner), is gone with the request, let alone a restart. **The agent never sends an identity**: `handleMcpToolCall` looks the person up from the task its token is bound to, exactly as the launch path looks up whose credential to spend, and `mcpActor` returns a bare role wherever no person was resolved — which is also what keeps a person off an outbound RPC, where `applyCallerActor` would 403 it.

Every `role: 'agent'` turn is written through one of two helpers, and choosing between them is the call site's job. `createAgentTurn` resolves the person from the SESSION and is for a row written while that turn is the one running. `createRecoveredAgentTurn` takes the owner explicitly and is for a row written for a turn that is already OVER — a displaced response swept up after a newer turn launched, an abandoned or stopped claim settled by whoever ticks next. Reading the session there names the person who asked for the NEWER turn, which is worse than a stale owner: it puts one person's work and token spend on a row naming another, append-only. The owner comes from the in-flight CLAIM, which captures it at launch (`InFlightTurn.turn_owner_email`), or is `null` when nothing that survived the turn names anybody — nobody is correctable later, the wrong person is not. `test/unit/turn-owner.test.ts` scans for a call site that bypasses both.

A row carries ONE person, and the helper REFUSES two: an `actor` that names a person plus a different owner throws rather than merging, because merging silently drops one of two humans and which one it drops depends on whether the other argument happens to be set. Decide what the row records. An ACTION row (a stop, whose content is "Stopped by user: …") keeps its actor whole and passes a null owner; a TURN row passes the owner and an actor that names only a channel.

A launch that runs BESIDE a task rather than as one of its turns — today the builder behind a review conversation — passes `spender` to `planTurnCredential`, never runs as the task's turn owner and records none. The owner decides a name as well as a credential, and a reviewer is not the person who asked for the task's next turn. It also binds and releases under a key of its OWN (`withReviewSessionCredential`, like `withDescribeCredential` / `withCompactCredential`), never the task id: one binding exists per key, so binding under the task's re-pointed a running turn's placeholder at the reviewer and the release revoked it, killing that turn with a 401. Details: [docs/design/actor-identity-and-remote-clients.md](docs/design/actor-identity-and-remote-clients.md) §3.3 case 2.


### Work nobody asked for is attributed to the account that configured it

"Nobody asked" is not "nobody is named". A turn the daemon starts by itself records no asker (above), and the rows it writes name the CONFIGURED SYSTEM IDENTITY under the role `system` — resolved by `resolveSystemIdentity` / `systemActor` (`src/identity/system-identity.ts`) from exactly two sources and never from anything else. In managed mode it is the `ownerEmail` the control plane pushed BESIDE the service credential (`putUserCredential`), which is the member whose Anthropic account those turns already spend; on a laptop it is the git identity, because in single-person mode all three cases collapse to one configured identity (§3.4) and **the role is then the only thing distinguishing "they typed it" from "their daemon did it by itself"**. Nothing is derived from the credential's `label` (free text an operator may set to anything) and nothing is derived from the last human to touch the task. Where neither source answers — no owner pushed, no git config, no project root — every call site gets back the BARE ROLE it passed before this existed, so an unconfigured install keeps exactly the rows it had. A project with no service credential at all is unchanged in both halves: its automations stay disabled with `NO_SERVICE_CREDENTIAL_MARKER`, and no identity is invented for turns that therefore never run.

The identity is resolved AT WRITE TIME, never stored on the session. That is what keeps the two questions apart: `Session.turn_owner_email` answers who ASKED and stays empty, which is the record the fail-closed clearing above protects.

**Which turns get it is a RECORDED FACT, never an absent field.** `Session.turn_system_initiated` is written by the same launch write that clears the owner, and cleared by the one that records a person; `personForCurrentTurn` reads the MARK, and an unmarked session with no owner names NOBODY. The inference is unavailable because absence has other causes — a best-effort person write that failed, a session predating the field, a store that never got the write — and every one of them must degrade to the pre-identity shape rather than to a claim that a specific account's automation did the work. The person branch's failure path therefore CLEARS rather than leaving the previous record standing, which is also what makes its own warning text true.

Two writers apply it, and choosing between them is the call site's job — the same shape as `createAgentTurn` / `createRecoveredAgentTurn`, and they share one resolution (`personForCurrentTurn`) so an agent's turn row and the supervisor announcement beside it cannot disagree. `createAgentTurn` swaps the `agent` CHANNEL for `system` when nobody asked; `turnChannelActor` KEEPS the caller's channel and only adds the person, because `supervisor` on a sync turn is what `recordSyncTurns`' content-based idempotency check reads back and a role that differed between two passes over one response would record the same merge twice. A sync a human typed keeps that human, not the system account — the session owner wins wherever there is one. `createRecoveredAgentTurn` deliberately does NOT fall back: a row written for a turn that is already over may have belonged to a person nobody can name any more, and "nobody" is correctable while a wrong claim is not.

**THE BOUNDARY IS THREE MODULES, and it is narrower than "the daemon's own rows".** `systemActor(projectRoot)` is applied in `src/utils/reconcile.ts` (every `'system'` status change and park it writes), `src/utils/auto-resume.ts` and `src/daemon/auto-deliver.ts` — the reconciler proper plus the two turn-launching automations. Every OTHER daemon-initiated `'system'` writer deliberately still passes the bare role: `stranded-merge.ts`, the async-claim settlements in `task-lifecycle.ts`, and the comment writers in `auto-react.ts` and the parent-notify path. That is pending a check of each one's READERS, not an oversight to tidy up — an `actor` is read as the CHANNEL by code that decides behaviour (`createdByOwnAgent`, the reason the MCP door is an exception below), so widening one means first proving nothing downstream keys on the bare string. Convert none of them without doing that.

MCP writes deliberately do NOT take it either: `actor` on that door is read as the CHANNEL by code that decides behaviour — `createdByOwnAgent` (`src/daemon/loop-restart.ts`) asks whether a new child's creating actor was `agent` to tell the loop's own subtasks from ones a human added — so a loop whose turn the reconciler had resumed would have started answering "somebody else" to its own children and woken itself forever. Those rows keep naming the channel and nobody, exactly as before; widening them means giving each such reader the distinction first.

### One resolver decides a task's current prompt

Prompts are versioned, but "the current prompt" is not a history read: `updateTaskPrompt` writes `task.prompt` in the same operation as the new version, and every surface that wants it calls `currentPromptOf()` (`src/task-prompt.ts`). `getPromptHistory` is for HISTORY — never index into it for "current". FileStorage sorts it NEWEST-first, so `history[history.length - 1]` is the OLDEST prompt: callers doing that served the ORIGINAL text after a `lazy edit --prompt`, and `lazy_show` showed a prompt the agent never received while `lazy clone` / `redo` seeded new tasks with the superseded one, which was then executed. Do not "fix" the ordering to make indexing safe — it is asserted in `test/unit/storage-concurrent-writes.test.ts`, and invariant tests are not an agent's to edit.

### Storage is abstracted — never bypass it

All persistent state (tasks, sessions, turns, commits, comments, conversations) goes through the Storage interface (`src/storage/interface.ts`). Never read/write `.lazy/` or other stores directly from CLI commands or other modules — FileStorage is just one backend. New entity type → add Storage interface methods first, then implement in FileStorage.

**Carve-out: disposable telemetry is not storage state.** Bounded, project-local, throwaway streams live OUTSIDE Storage deliberately; the one instance today is the proxy audit log (`src/proxy/audit-log.ts`, `.lazy/logs/proxy-audit.jsonl`), which inside the store grew to 677 MiB and broke a store push. Do not "fix" it back into Storage. Anything new claiming this carve-out must be bounded by construction (rotation or hard cap) and disposable — if losing it costs the user anything, it belongs in Storage.

### The daemon owns business logic — CLI, MCP, and supervisor are clients

The daemon is the heart and brain: all business logic, storage access, and state management live there, behind its RPC. The CLI is a human-facing client (parse input, format output, prompts), MCP an agent-facing client (tool schemas, pushback/confirmation), the supervisor an agent-lifecycle client. Violations to reject on sight: opening storage from CLI/MCP/web code, re-implementing a business rule in a client, or spawning the lazy CLI from the daemon or an MCP handler. In tests, mock at the external boundary (agent process, forge APIs, Docker) rather than internal seams.

**The mechanical form: `src/daemon/` and `src/server/` import NOTHING from `src/cli/`.** Both counts are zero and `test/unit/daemon-cli-decoupling.test.ts` keeps them there — mechanical because the drift never arrives as one reviewable violation, but as dozens of individually unremarkable imports across a release. If the daemon needs something that sits under `src/cli/`, that thing is domain logic in the wrong place: move it to the module that owns the concern (`src/task/`, `src/render/`, `src/credentials/`, `src/preconditions.ts`) rather than importing across the boundary. `docs/design/module-boundaries.md` maps where things live.

### Tests encode invariants, not just current behavior

Every test encoding a design decision gets a comment in the form `// INVARIANT: <the rule>. <why it exists>`. Never add tests that assert the absence of correct behavior. Never modify or delete an existing invariant test without human approval — if a test seems wrong, ask; don't "fix" it to match your new code.

### `process.exit()` belongs to CLI commands, not to shared helpers

A helper that exits on failure is a landmine for every long-lived process reusing it: one daemon-unreachable `lazy_status` killed the stdio MCP server mid-request, taking every remaining `lazy_*` tool with it for the rest of the turn. The pattern is a throwing core plus a thin exiting wrapper. `resolveLazyRoot()` / `resolveStorage()` throw `LazyPreconditionError` and live in `src/preconditions.ts`, outside `src/cli/`, precisely so a long-lived process can reach them without importing a CLI module — use these in ANY long-lived process (MCP server, daemon, supervisor). `requireLazyRoot()` / `requireStorage()` (`src/cli/helpers.ts`) catch it, print `Error: <message>` and exit 1; CLI commands only.

Before adding a `process.exit()` outside `src/cli/`, check who else calls the function. If a server can reach it, throw instead — the JSON-RPC layer turns a thrown error into a tool error and keeps serving.

### Skipping confirmations: `--yes` on the CLI, `confirmation_code` over MCP

Two mechanisms; do not conflate them. Non-interactive CLI invocations (supervisors, scripts) skip confirmation prompts with `--yes`, and every command with a confirmation prompt should accept it. MCP tool handlers never shell out to the CLI and never use `--yes`: they return a `confirmation_code` the caller must echo back (`src/mcp/confirmation-context.ts`). Neither surface may use `LAZY_PROMPT_DEFAULTS`, which is test-only.

### Documented short flags must be registered as parseFlags aliases

`parseFlags` registers `--<name>` only; a single-dash spelling exists only if declared, e.g. `{ name: 'message', aliases: ['m'], takesValue: true }`. Documenting a short flag in usage text without the alias ships a broken flag — always add both together; `test/unit/cli-flag-alias-coverage.test.ts` scans every `<name>Usage()` against its `command<Name>()` flag table.

Never register `--help`/`-h` as a command's own flag: the dispatcher in `src/index.ts` intercepts both first, so such a flag is dead code and a `-h, --help` usage line is noise.

A flag table shared between commands (`RAISED_RESOLUTION_FLAGS` in `src/cli/raised-resolutions.ts`, spread into `accept` and `unblock`) must stay a plain `export const <IDENT>: FlagDefinition[] = [...]` array literal, imported directly by each command. `test/unit/cli-command-discoverability.test.ts` is a source scan that follows the import and reads the literal; building the table from a function call, a barrel re-export, or `concat` makes the guard unable to see the command's real flags, and it fails loudly (`unresolvedTables`).

### Multiplexer subcommands must be listed in the parent's usage map

`lazy system <sub>` and `lazy daemon <sub>` route `-h`/`--help` through `<parent>SubcommandUsage` in the dispatcher. A subcommand with its own `<name>Usage()` missing from that map silently prints the PARENT's help, with no error anywhere — add the map entry with the subcommand. `test/unit/cli-subcommand-usage-coverage.test.ts` cross-checks both directions.

### A task worktree's lazy.toml has no authority

Every config read resolves to the PROJECT ROOT's `lazy.toml`. `loadConfig(lazyRoot)` takes no starting directory and `findConfigDir` does not walk up (`src/config/loader.ts`) — anchoring lives in the loader, not in call-site discipline, because a per-caller rule is one new launch path away from being wrong again. There are no per-key carve-outs.

The config sits on an agent-writable branch, so loading a turn's config from the worktree let a turn choose the rules its NEXT turn ran under: blank `[permissions] protected` (which defaults to `[]`, so the edit is not itself flagged), blank `[checks] post_turn`, zeroed watchdog, dropped `[[maintain]]` groups, its own model and effort. It also wedged tasks — a branch carrying a config shape the daemon rejects made both `unblock` and `sync` fail, and sync was the only way to bring the fix in.

`LAZY_CONFIG` still works: an absolute path is used directly, otherwise it names the file to read **in the project root**. If a per-task setting is ever wanted, it follows the container-image pattern below — explicit human TTY consent, pinned on the task record — never a file on the branch. Invariant tests: `test/e2e/worktree-config-authority.test.ts`, `test/unit/config-root-anchored.test.ts`.

### Task worktrees never auto-govern container images; human TTY consent only

A task worktree's `Dockerfile.lazy` must never silently pick the container image: task branches are agent-writable, and deriving the image from one would let an agent's Dockerfile edits run as build steps under the daemon's docker on the HOST, outside every container guard. Launch paths (`launchSupervisorAsync`, `runClaude`, `ensureImage`) never anchor image resolution at `sandbox.worktreePath`.

There are exactly two human-consented exceptions, both **CLI TTY only**: a **per-task pin** (`lazy create` / `start` / `edit` asks once, default NO, and stores the image on the task record) and an **upgrade adoption** (`lazy upgrade` announces any existing adoption and prompts to keep it, default YES; a new worktree Dockerfile is offered default NO). Non-TTY, `--yes`, MCP, builder and scripts are never prompted and always use the root-resolved image or a valid adoption; there is deliberately no MCP surface for choosing images. Consent is never inherited past its subject: adoption is cleared without a prompt when the Dockerfile drifts from the consented hash, the path is gone, or the adoption's version no longer maps to this binary's image tag.

**If a stored or adopted image is missing at launch, fail loudly** — never fall back to the root image. Launches soft-pin the stored image NAME and never re-hash the worktree path, so a post-consent agent edit cannot become a host docker rebuild.

**Build context follows the consented Dockerfile** (engineer-approved amendment, 2026-09-06): a consented worktree Dockerfile builds with **that worktree directory** as the build context — never the project root, which is the bug this rule prevents — while the Dockerfile bytes stay the consented temp copy; the plain root `[docker].dockerfile` keeps the project root as its context.

**Launch resolution order:** (1) task's stored `custom_image`; (2) valid daemon-adopted image; (3) root `[docker].dockerfile`, which `resolveCustomDockerfile` (`src/capture/claude.ts`) joins to the PROJECT ROOT. There is no env-var override. Where consent is stored, how each hash is computed, and the full expiry rules: [docs/design/worktree-image-flow.md](docs/design/worktree-image-flow.md).

### `public-docs/` is published; `docs/` never leaves this repo

Two documentation trees split by AUDIENCE, and the directory is the whole policy — there is no per-file allowlist.

- **`public-docs/`** ships in the public source repo (`.releaseinclude` takes `public-docs/**`) and renders to `docs.getlazy.dev` — world-readable the moment a release is cut. Write for someone who cannot see our tasks: no internal jargon, no task codes, no unreleased or planned work, no spike/review deliberation, no internal infrastructure. Every page `src/docs/links.ts` points at lives here, because lazy's own error messages link to it.
- **`docs/`** is internal and ships nowhere: spikes, research, reviews, design notes, runbooks, obsolete designs, the builder's `scratch/`. Future plans and deliberation belong here.

A public page must not link into `docs/` — the target does not exist for a public reader, and the link advertises internal material by name; write the substance into `public-docs/` instead. The split replaced a denylist over one mixed tree that named only `scratch`, and so put `docs/reviews/` and `docs/spikes/` on the public internet at the first real docs-site publish. A tree whose NAME states its audience cannot fail that way by omission.

### Prompts are for the user's project, not for lazy itself

Agent system prompts (`src/prompts/`) are injected into agents working on the USER's codebase. No lazy-internal design decisions, invariants, or implementation details in them — those live here in CLAUDE.md.

### Never use Bun.spawn/Bun.spawnSync directly

In `src/`, use the wrappers in `src/utils/spawn.ts` — they turn raw ENOENT (`posix_spawn`) failures into clear messages naming the missing binary or path, and they guarantee a timeout. The only exceptions are `src/utils/spawn.ts` itself and `src/qa/agent.ts`, which documents its own reason at the top of the file. Test code may call `Bun.spawn` directly.

There is no bare `spawnSync` export, deliberately: a sync spawn holds the whole thread (in the daemon, the event loop), so whether it may run unbounded is a decision the call site must make by name, not one an options bag makes silently.

- `spawn()` — async; timed out at `DEFAULT_SUBPROCESS_TIMEOUT_MS` (60s) unless overridden.
- `spawnSyncUnsupervised()` — sync, for a child nobody is watching (probes, version checks, `git`/`ps`/`docker` queries). Same 60s backstop; pass a shorter `timeout` where the command should be fast. Treat `exitCode: null` + `signalCode: 'SIGTERM'` as a possible timeout, not just a failed command.
- `spawnSyncInteractive()` — sync, for handing the TTY to the child (`lazy shell`, `tmux attach-session`). Never timed out; passing `timeout` is a compile error, because killing a session someone is actively using is a bug, not a backstop.

### Never use sync filesystem calls

Use `fs/promises`. Sync calls (`readFileSync`, `writeFileSync`, `existsSync`, `readdirSync`, `statSync`, …) block the entire event loop and have caused real production issues (reconciler starvation, blocked HTTP handlers) — and sync calls in "cold" code migrate into hot paths unnoticed. Acceptable **only** in: CLI startup/init before the event loop matters, process exit handlers, test setup/teardown. Any other sync call needs a comment explaining why async isn't viable.

### Fail hard on remote failures — no silent fallbacks

Remote operations (push, fetch, MR/PR creation) retry up to 3 attempts with progressive backoff (2s, 4s) — use `withRemoteRetry()` from `src/utils/retry.ts` in drivers. If all retries fail, the operation FAILS: no silent fallback to local-only behavior, and `success: true` with a warning is NEVER acceptable. The caller decides how to handle failure, not the utility function.

Before a remote merge (accept), the parent branch's local commits MUST be pushed first — otherwise the remote parent gets the merge commit without them and diverges.

This does not conflict with the accept commit point below: a parent push that fails AFTER an accept's merge is still reported as a failure (non-zero exit, named step, retried, system message if it persists) — it just no longer un-accepts work that has already merged.

### The git merge is an accept's commit point

Engineer's rule (2026-09-22): **nothing that can fail runs between the merge landing and the task becoming accepted.** `acceptTaskRun` (`src/daemon/task-lifecycle.ts`) has three bands. BEFORE the merge: every gate, approval, check, the pre-merge parent push and the description refresh — any may refuse, and only here may `abortMergePhase` restore the prior status. THE MERGE, then at once `commitAcceptTransition`: store writes only — `[Accepted]` comment with the original reason and actor (BEFORE the session ends: storage self-heals an ended `accepted` session to `complete`), session `accepted`, status `complete`. AFTER: fast-forward, parent push, accept tag, parent notify, reparenting, parent fidelity and cleanup are FOLLOW-THROUGH (`runAcceptFollowThrough`), recorded as pending under the `accept_followthrough` task metadata, idempotent, a failure blocking only the steps that depend on it (cleanup and token revocation never wait on a failing push), retried by the daemon's Sweep 9b with backoff, loud (the accept result carries `followThroughPending`, the CLI exits non-zero, a system message after repeated failures), and never able to move the task out of `complete`. Every accept exit that merged — local, forge-immediate, both forge re-entry paths, and remote-sync / `syncTaskFromRemote` seeing a PR merged (under the task's lifecycle lock, which is an in-process map — it excludes anything only because `syncTaskFromRemote` runs solely in the daemon; the CLI review flows reach it through the `syncTaskFromRemote` RPC and must never import it) — goes through the same pair. Do not put a fallible step back between the merge and the transition, however small: that window is what left merged work on `merging`/`blocked` tasks in the field, repeatedly.

**A dead accept is RESUMED, never restored.** `beginMergePhase` persists the accept intent (reason, actor, approvals) next to the in-flight marker; the stranded-merge sweep (`src/daemon/stranded-merge.ts`) re-runs the accept from it, and the local squash is idempotent on resume only (`MergeOptions.resume` → `alreadyLanded`, decided from the trees, never a git tag — task state lives in the store). A fresh accept of a net-empty branch still refuses. A resume FIRST asks the trees (`acceptWorkLanded`): work already on the target — or a session already `accepted` — is finished before preflight and every gate. Otherwise it re-checks none of the accept's POLICY gates (violations, raised items, review issues, branch in-sync, forge approval, pre-merge CI gates, `[automation.pre_accept]`); only data-safety checks (dirty worktree, pairing lock, an active parent) still run. It never calls `abortMergePhase`. While a resume is pending, reject/close/submit/unblock refuse; after `MAX_ACCEPT_RESUME_ATTEMPTS` failures the daemon files a system message and the escape reopens — but it too asks the trees first and refuses (pointing at `lazy accept`) when the work has landed, so neither the fix-stranded-merging wedge nor the 2026-09-08 incident can return. Hosted drivers recognise a landed SQUASH on resume from the trees too (their ancestry check cannot). A forge-pending merge (no marker) stays the forge's. Details in [docs/design/accept-commit-point.md](docs/design/accept-commit-point.md).

### PRs only for protected branches

By default PRs/MRs are created only when merging into a protected branch (one where non-admins cannot force-push or merge without review). Subtask→parent merges are local git operations, never remote MRs: accept routes every intermediate (task-branch) target through `mergeLandsLocally()`, no automatic path (accept's remote-ref step, the pre-review sync in `src/task/sync-remote.ts`) opens one, and the drivers refuse to DERIVE a task-branch base.

**An explicit submit by a person is the one exception** (engineer decision 2026-09-24): "we should never open a PR/MR for intermediate branches, but I literally asked for this." `lazy submit` on the human channel — the CLI, the dashboard's Submit, Teams — on a task whose target is an intermediate branch opens the PR/MR with the parent task's branch as its base, passed to the driver EXPLICITLY (`markReadyForReview(task, { baseBranch })`), and records it like any submitted task, so auto-react, the description refresh and every PR link work unchanged. The rules live in `src/daemon/submit-target.ts`, shared by the preflight and `submitTask`:

- **Who may not:** the MCP door. `lazy_submit` — builder and task agents alike — keeps the refusal, because the preflight is asked AS the caller's channel; an agent cannot tell a person's explicit ask from its own initiative. Listed in [public-docs/surface-asymmetries.md](public-docs/surface-asymmetries.md).
- **The base must already be on the remote.** Submit never pushes the PARENT to make it so (the sync rule above); it refuses and names the fix.
- **A PR/MR a person opened by hand is ADOPTED**, for any task, never duplicated — and refused when its base is not where the task integrates (for a root task with no named target, the remote default's real name), so lazy's record cannot disagree with the forge.
- **Accept still merges locally.** `mergeLandsLocally()` is unchanged and stays the single routing predicate. Because the forge cannot see a local squash as a merge of that PR, the accept's follow-through CLOSES it (`close-review` step: idempotent, retried, no comment; owed according to the CONFIGURED forge, so an offline accept closes it once back online; held until `push-parent` lands) — a local merge of any task with an open PR, not only an intermediate one. A linked task's PR belongs to someone else and is never closed. If a reviewer merges it on the forge instead, remote-sync completes the task exactly as for any forge-merged PR.
- **A PR's base must follow the task's target** (review round 3, a data-integrity fix). A PR's base is fixed when it is opened, and remote task branches are never deleted, so a subtask's PR still based on its parent's branch after the parent was accepted would, merged on the forge, land the work in the dead parent branch while lazy called the task complete. Every reparent the daemon performs (accept's, close's, `lazy reparent`, a parent closed on the forge, the zombie finalize, the orphan retarget in unblock and start, the stale-parent-chain rewrite in unblock's and sync's parent resolution) RETARGETS the open PR onto the new target — two target writes outside the daemon do not (the agent-side parent resolution in `src/mcp/internal-git.ts`, the CLI's `lazy reopen`; neither holds forge credentials), and there the base checks below are the backstop — (`retargetReview`: `gh pr edit --base` / `glab mr update --target-branch`, `src/daemon/review-retarget.ts`); if the forge refuses, lazy CLOSES it — writing a `lazy_closed_review` marker FIRST (`src/daemon/lazy-closed-review.ts`), so a CLOSED read on any later pass is settled as lazy's own close and never abandons the task or moves its children, and a resubmit asks the forge before REUSING a marked record (closed → dropped and a new PR opened against the current target; open → marker cleared; unreadable → refused, marker kept), and any PR a resubmit keeps has its base READ and, if it is not the current target, moved there — a refused move or an unreadable base refuses the submit, never a second PR, and a LINKED task's PR (`lazy link`) is never moved: a differing base refuses the submit, because that PR's base is its owner's to change (`recordedReviewBase`, `src/daemon/submit-target.ts`) — drops the record from the task once the close is confirmed, and a `submitted` task goes back to `blocked` — the one use of the `submitted → blocked` edge, decided on a FRESH read under the task's lifecycle lock so a task someone unblocked meanwhile is never marked blocked while its agent runs. A forge that cannot be asked (offline, or an unreadable PR state) leaves a `[PR not retargeted]` comment rather than skipping silently — and after a close, only a forge that SAYS `CLOSED`/`MERGED` confirms it: an unreadable state keeps the PR record (the guards below need it to see the PR) and, in the accept's `close-review` step, stays owed and is retried. The backstop is `src/daemon/review-base.ts` — which exempts LINKED tasks (`lazy link`), whose PR lazy never opened or reparented and whose base is its owner's, exactly as the retarget and `close-review` do: a forge accept refuses when the recorded PR's base is not the accept's target (for a root task with no named target, the remote's DEFAULT branch — `reviewComparisonTarget` — never the literal `main`), and remote-sync never completes a task whose PR was merged into another branch (it files one alert instead).

### Lazy writes NOTHING to a PR that notifies a human

The complete list of forge WRITES is three items, and it is closed: **create** the PR/MR (`lazy submit`), **keep its lazy-owned description section current** (`updateRemoteBody`, run by the sync sweep through `refreshFidelityForNewWork`), and **`approveForMerge`** — an approving review submitted ONLY under `[remote] auto_approve` on a protected target, where the forge refuses the merge without one, which makes it the merge mechanism rather than narration. A description edit notifies nobody; the approval is off by default and deliberately asked for. Besides those three, lazy only ever CLOSES a PR/MR it tracks — when the task is rejected or closed, when its work was merged locally, and when a reparent could not move it (see above) — and RE-BASES one onto a reparented task's new target, both with no comment attached: a PR left open, or left merging into the wrong branch, would claim something about the work that is not true. Nothing else may be added. READING the forge (auto-react, `sync-remote`) is untouched.

The mechanism this replaced was large: `postReviewReport` posted every review's findings as PR comments — with fix rounds, several batches per task — plus `postAcceptReview` on three accept paths and `postRejectReview` on reject, and lazy also mirrored agent turns as comments. Every one of those notified everybody watching the pull request, which is what people complained about. So the engineer's decision (2026-09-21) was REMOVAL, not configuration: "Description refresh is fine — that's a single thing that gets updated. Intermittent comments are not fine — we should just not post anything." **There is deliberately no opt-in key**, and adding one is the regression — a `[remote] post_review_findings` was half-built and discarded on the way to this. `lazy review --post` and `lazy_review`'s `post` parameter are gone; the CLI flag stays registered as a no-op that says so, exactly like `lazy doctor --no-resume`, so an old script does not die on an unknown flag.

A review lands on the TASK and is read there (`lazy show`, the Reviews tab, the review page); findings reach the implementer as fix feedback. An accept or reject reason lands on the task as a `[Accepted]`/`[Rejected]` comment and in the merge commit. A failed approval under `auto_approve` returns a warning and posts NOTHING — the old comment fallback was pure noise, since a comment is not an approval and never unblocked the merge. Guards: `test/e2e/review-verb.test.ts` asserts a review on the task's own PR makes no forge write, and the driver suites assert the three removed methods do not exist on `LocalDriver` / `GitLabDriver` at all. Retired design note: [docs/design/review-comments-to-pr.md](docs/design/review-comments-to-pr.md).

### The MCP surface is deliberately narrower than the CLI

Humans and agents make different mistakes, so CLI and MCP are not mirror images. Agent-ownership gating, two-step `confirmation_code` friction, "MCP never auto-starts work", the human-only `lazy protect`, and the TTY-only protected-merge passphrase at `lazy accept` are design decisions, not gaps — do not "fix" them into symmetry. The full list with rationale is [public-docs/surface-asymmetries.md](public-docs/surface-asymmetries.md): read it before filing a CLI/MCP difference as a bug, and add to it when introducing a deliberate asymmetry. Differences NOT listed there are probably real gaps — [docs/reviews/cli-mcp-parity-audit-2026-08.md](docs/reviews/cli-mcp-parity-audit-2026-08.md) classifies the known ones.

## Working Like a Team Member

Rule of thumb: **"Would I as a reviewer do this?"** The human reviewer approves your work; you are responsible for making it merge-ready.

- **Merge conflicts are yours to resolve:** merge the parent branch in, resolve, verify correctness, run tests, commit with a clear message. Never leave conflicts for the human.
- **NEVER commit to `main`.** Verify you are on your task branch (`git branch --show-current`). In a worktree, use the worktree path for ALL git operations — `cd`-ing to the parent repo and committing there lands changes on `main`.
- Commit at logical checkpoints; multiple small commits beat one large one; explain design decisions in commit messages or code.
- Do NOT commit secrets/credentials, build artifacts, `node_modules`, or IDE files unless explicitly part of the solution.
- If requirements are unclear, ask for clarification.

## Code Quality

Follow existing code style; add comments only where logic isn't self-evident; test your changes.

### Error handling: never swallow, always surface

Every `catch` block either handles the error meaningfully or propagates it with context:

1. **No empty `catch {}` blocks** — ever, including `catch { /* ignore */ }`. A genuinely-safe suppression needs a comment saying exactly why and what you verified.
2. **Add context when re-throwing.** ``throw new Error(`failed to parse ${configPath}: ${err.message}`)`` — not a bare `throw err`.
3. **Don't catch-log-continue when the operation failed.** If the function can't do its job, throw; the caller decides what to do.
4. **Distinguish "not found" from "found but broken."** A missing config file falls through to defaults (`err.code === 'ENOENT'`); one that exists but won't parse is an error the user must see immediately — re-throw with context.
5. **Errors are for humans.** Say what happened, what was being attempted, and what to do about it — with the actual values (paths, keys, expected vs actual).

### Principle of least surprise

- **Commands do what their name says** — `lazy accept` accepts; no silent rebases or extra side effects. If a command must do something extra, tell the user first.
- **No hidden side effects** — writing `~/.claude.json`, starting background processes, touching unmentioned branches are bugs unless explicit and visible.
- **Errors are actionable** — "Docker not running. Start Docker Desktop or configure `runner = "host-process"` in lazy.toml", never "Error: command failed".
- **Flags do one thing** — no magic values or mode-switching overloads.
- **Defaults are safe** — destructive or risky behavior requires explicit flags; never make the dangerous path the easy path.

### Fix root causes, not symptoms

Never paper over a performance bug with pagination, caching, or lazy-loading. If something is fast after a daemon restart and degrades over time, the bug is in whatever is accumulating state — fix that, not the display layer. First diagnostic question: slow from the start, or degrading?

### Never present a guessed cause as the explanation

When something fails, read the actual code path before asserting why. A plausible-sounding fabricated cause ("must be a protected-branch rule") is worse than "I don't know yet, let me check" — in summaries, reviews, and error analysis alike. If you can't verify a cause, say so and investigate.

### Clever ain't wise

- **Straightforward over magical.** Don't auto-detect, auto-infer, or auto-correct when explicit input is available; if something is ambiguous, ask rather than guess.
- **Consistent over convenient.** Same patterns across commands — if `accept` takes `--yes`, so do `reject` and `close`. No per-command special syntax.
- **Transparent over terse.** Narrate what's happening ("Merging upstream into task branch..."); the user should never be surprised by what `git log` shows after a lazy command.

## Security

Never commit sensitive information. Validate user input at system boundaries. Parameterized queries only — never string concatenation for SQL. Mind the common vulnerabilities (XSS, SQL injection, etc.).

## Logging

Lazy's central logger is `src/utils/logger.ts` (console and log files, timestamps, verbose/debug flags). Use `logger.info/warn/error/debug` for all output after logger init. `console.*` is allowed **only** for: pre-logger startup code (`src/index.ts` early startup, `src/config/loader.ts`, `src/cli/init.ts`); explicit debug-mode output (prefix `[DEBUG]`); help/usage text; and final formatted output (summary tables, task listings, status reports).

**CRITICAL: never duplicate a message at different layers of the application.**

## Prompts

All prompts (system prompts, task templates, goal context) live in `src/prompts/` as `.md` files — never inline prompts as string literals. Import with `import myPrompt from '../prompts/my-prompt.md' with { type: 'text' };` so prompts stay discoverable, diffable, and editable without touching code. Variable substitution uses `{{placeholder}}` syntax and `.replace()` at the call site.

## CHANGELOG style

Written for people outside this repo: a 30-second scan of what's new, changed, or fixed — not how it was built (that depth lives in the task, which they cannot read).

- **One line per entry**, stating the user-visible effect, not the implementation. No internal type/function names; command names, config keys and flags are fine — they're the user surface.
- **Never reference task codes.** The audience cannot look one up.
- **Intro paragraph: 3 sentences max.** Keep the `Added` / `Changed` / `Fixed` structure; don't rewrite older sections to match.

Example: ``- **`lazy daemon list` / `kill-stray`** — see and reap stray daemons host-wide``

## End-to-End Testing

The e2e suite in `test/e2e/` runs CLI commands as subprocesses with mocked agent responses. **Any new command or behavior change needs e2e coverage:** new command → new `test/e2e/<command>.test.ts`; behavior change → extend the existing file; bug fix → a test reproducing the bug first.

The rules below are the ones you must know before you can go wrong. The harness's operating detail — the `TestContext` API, scenario builders, the three leakable process classes and their reapers, the four daemon-isolation axes, the container-vs-Mac unit-test traps, the builder-supervisor preflight, per-variable env-var reference, and the five env-leakage rules — lives in [docs/testing-harness.md](docs/testing-harness.md). Read it before writing a suite that starts a daemon, drives a supervisor, or spawns its own subprocess.

### Running tests

```bash
bun test test/e2e/create.test.ts       # single file — the supported mode
bun test --timeout 30000 test/e2e/     # multi-file: --timeout REQUIRED
bun test                               # whole suite (slow suites skipped)
LAZY_SLOW_TESTS=1 bun test             # include the opt-in slow suites
```

**During a turn, run the tests that cover what you touched**, plus whatever type-check or lint is cheap — not the whole suite, which costs minutes on every turn while the project's post-turn check already runs after you. **Full verification happens ONCE, at pre-accept**, in the task's worktree: the FULL unit suite (`bun test test/unit/`), because a signature change elsewhere can leave a pre-existing test stale while everything task-local passes. Classify any failure as pre-existing vs introduced by verifying it yourself, never by relaying the agent's claim.

**Multi-file runs require `--timeout 30000` on the command line**, and it is the ONLY working mechanism: bunfig's `[test] timeout` key is silently ignored by bun (never add it back), and `setDefaultTimeout()` in the preload reaches exactly ONE file per run — every other file falls back to bun's 5000ms, under normal e2e wall-clock. Hence bare aggregate sweeps invent hundreds of phantom `timed out after 5000ms` failures: **a bare multi-file `bun test` result is not evidence of anything.** The npm scripts pass the flag (`test/unit/test-timeout-coverage.test.ts` keeps them honest); a per-test `test(name, fn, ms)` override still wins.

**Per-file execution is the supported mode.** Each `withDaemon: true` suite starts a real daemon on a port from a bounded window (26024+); full-directory runs spin up many, and any suite omitting `ctx.cleanup()` in `afterEach` leaks daemons that exhaust the window and fail later suites with spurious bind errors. Treat a green per-file run as authoritative and a red full-suite run as suspect until reproduced per-file. The `TestContext` API and the canonical suite skeleton are in [docs/testing-harness.md](docs/testing-harness.md).

**Three skip gates, and a skip is never a pass** — each prints one line per skipped file so a default run is never silently green-by-omission. Slow suites (`test/e2e/daemon.test.ts`, `remote-storage.test.ts`, >300s each) run only under `LAZY_SLOW_TESTS=1` via `slowSuiteSkipped()` (`test/helpers/slow-suite.ts`) — run them before touching the daemon or RemoteStorage, and at pre-accept. Suites launching an agent under the OS sandbox need `bwrap` and `socat` on PATH (packages `bubblewrap`, `socat`; without them `checkAvailability()` aborts before any assertion) and self-gate with `sandboxSuiteSkipped()` (`test/helpers/sandbox-deps.ts`); `Dockerfile.lazy` ships both, so do NOT `apt-get install` them — if they are missing your image needs a rebuild (`docs/agent-container-lazy-dev.md`). Suites needing a second loopback address gate with `secondLoopbackSuiteSkipped()` (`test/helpers/second-loopback.ts`), since macOS's `lo0` has only `127.0.0.1`.

**Gate only what actually needs gating.** Only a suite passing `hostPermissionMode: 'sandbox'` touches the sandbox — fake-binary suites default to `permission_mode = "bypass"` — and config-surface/argv-only suites (`test/unit/host-sandbox-posture.test.ts`) never spawn an agent and need no gate at all.

**Unit tests carry their own container-vs-Mac traps**, which produce failures that look like the code under test: `realpath` a temp root before comparing against paths git printed (macOS `tmpdir()` is `/var` → `/private/var`, so hand-composed paths never match git's spelling), and make a stand-in "other program" process a SYMLINK to `/bin/sleep` via `startForeignProcess()`, never a copy (copying a system binary trips macOS code-signing at exec). All three in full: [docs/testing-harness.md](docs/testing-harness.md).

**Three process classes leak: daemons, supervisors, and machine one-shots.** Each has reapers that only work if you spawn through the harness — route any new daemon-spawning path's env through `setupTestLazy`'s helpers so it inherits `LAZY_TEST_PARENT_PID`. A leaked supervisor is not just clutter: Claude Code reads ONE MCP config per HOME, so stray test supervisors once re-pointed a real agent's tool channel at a deleted worktree. Machine one-shots (`runOneshot`) always run in a throwaway container, never a bare agent binary on the host, and are BOUNDED by default. Details and the full reaper list: [docs/testing-harness.md](docs/testing-harness.md).

**Isolate daemon state with the purpose-built seams, never `HOME`:** `LAZY_DAEMON_BASE_DIR` for socket/PID/token/log/lock, `LAZY_CONFIG` (via `pinConfig()`) for in-process daemons, and `LAZY_PASSPHRASE_BASE_DIR` — deliberately its own seam — for the approval passphrase. Redirecting `HOME` instead also moves credential discovery, `~/.gitconfig` and the default storage path, and behaves differently on a dev machine than in CI. Unpin `LAZY_DAEMON_BASE_DIR` AFTER `ctx.cleanup()`, never before, or the daemon is never reaped.

### Two agent seams: the module mock and the fake binary

**1. The module mock (default).** `test/mocks/claude.ts` replaces all of `src/capture/claude.ts` via `--preload`, including `launchSupervisorAsync`. Fast; right for "a turn happened and produced this response" — status transitions, accept/unblock flows, CLI output. Structural limit: everything downstream of `launchSupervisorAsync` (watchdog kills, SIGTERM→SIGKILL escalation, stream-json parsing, response capture) is replaced and unreachable.

**2. The fake binary (`setupTestLazy({ fakeClaude: true })`, implies `withDaemon: true`).** Installs a scriptable fake `claude` on PATH and switches to the host-process runner; nothing in `src/` is mocked — the daemon really launches `lazy supervise`, which really spawns the fake agent. Use whenever the behavior under test IS the supervisor: watchdog kills, the agent argv contract, stream-event handling. `{ fakeCursor: true }` is the same seam for `cursor-agent`, mutually exclusive with `fakeClaude` (one PATH, one `agent_id`).

**A wire format is never invented.** The cursor fake emits only the `stream-json` objects read off the shipped bundle; anything beyond the verified objects must be read off the bundle first, naming the version. See [docs/cursor-stream-json.md](docs/cursor-stream-json.md) and [docs/fake-agent-binary-seam.md](docs/fake-agent-binary-seam.md).

**The module mock must echo `command_id` on every response it writes**, exactly as the real supervisor's `writeCorrelatedResponse` does. The daemon correlates a synchronous turn's answer by it, and for an **ask** an uncorrelated response is never that turn's answer, so the ask polls until its supervisor is declared dead. For the same reason the mock handles `ask` on its own read-only path: a real ask never commits, so falling through to the committing work path would be a fidelity lie.

Stream-json event shapes must stay in sync with `src/agent/activity-stream.ts` and are built only in the per-agent fake, never inline in a suite. Watchdog guards — like every setting — are read from the **project root's** `lazy.toml`, so a test tightens them there. A watchdog kill lands the task in `interrupted` (auto-resumable), not `blocked`. Both seams in full, with their scenario builders: [docs/testing-harness.md](docs/testing-harness.md).

### Test-only env vars

**Never read a test-only env var from a production code path.** The full list with per-variable detail is in [docs/testing-harness.md](docs/testing-harness.md); the security-relevant ones are the three prompt seams.

**The three prompt seams — `LAZY_FORCE_TTY`, `LAZY_PROMPT_DEFAULTS`, `LAZY_PROMPT_SECRET` — are a complete non-interactive route to any prompt, including the approval passphrase.** Two guards keep that from being a real hole, and neither may be weakened to make a test easier:

- **They do not exist in a released binary.** `scripts/build.ts` passes `--define LAZY_RELEASE_BUILD=true --minify-syntax`, and each read in `src/cli/editor.ts` is written as an inline `typeof LAZY_RELEASE_BUILD === 'undefined' && …` so bun folds and eliminates the branch. Hoisting that test into a module-level `const` breaks the elimination silently (bun rewrites it to `var` when bundling), as does importing the flag from another module. `test/unit/build-release-flags.test.ts` bundles `editor.ts` both ways and fails if a seam survives, or if the build stops passing either flag.
- **`lazy system passphrase set|delete` refuses outright when any of them is set**, reading `process.stdin.isTTY` directly rather than through `isTTY()`. This makes the happy path of `set` un-e2e-testable **on purpose** — anything a test can drive, an agent running lazy from source can drive too. **Injection at the function boundary is the supported substitute**, not a weaker gate: `requireCurrentPassphrase`, `promptAndStore` and `offerLegacyCleanup` take their prompt as a parameter, so `test/unit/system-passphrase-gating.test.ts` reaches the behavior without the seam existing at runtime.

### Storage and config in tests

- **Test projects use EXTERNAL storage — never hardcode `<root>/.lazy/tasks`.** `lazy init` writes an `external_path` into the project's lazy.toml, so task state lives outside the temp repo. `test/helpers/storage.ts` is the ONE place that knows the layout (`tasksDirFor`, `taskFilePath`, `readTaskStatus`, `setTaskStatus`, `readSessionJson`, …) — use it.
- **Change a test's lazy.toml by EDITING the key, never by overwriting the file.** Rewrite the key in the init-produced file (`toml.replace('driver = "local"', 'driver = "github"')`) and assert the replace changed something. Overwriting with a stub throws away `external_path` (the command then sees an empty store and assertions pass for the wrong reason); appending a section init already writes is a TOML redefinition error; a `.replace()` that matches nothing is a silent no-op.

### Daemonless limits

- **A daemonless suite cannot `accept`.** The daemon reconciler is what moves a task out of `working`; daemonless it stays `working` forever and accept refuses. Accept tests need `withDaemon: true`, an explicit `lazy wait`, and their own worktree commit (the in-daemon agent uses the daemon's own mock response; per-test `LAZY_MOCK_SHOULD_COMMIT` never reaches it). Canonical pattern: `test/e2e/accept-reason.test.ts`.
- **Any command that runs a sync (`lazy sync`, `lazy reparent`) relaunches the task's agent**, so invoke it through `ctx.lazyMocked` even in a daemonless suite — plain `ctx.lazy` reaches a real runner and dies on `spawn failed: binary 'docker' not found`.
